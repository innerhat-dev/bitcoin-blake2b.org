Bitcoin Knots 29.4.1.knots20260508

Release notes for the BLAKE2b hardfork build.

Bitcoin Knots version 29.4.1.knots20260508 includes the BLAKE2b proof-of-work change, the reduced-data flag day, and a few spam-filter updates. Source is bitcoinknots/bitcoin. The files folder at bitcoinknots.org/files/29.x/29.4.1.knots20260508/ currently holds test builds only. Use the RC5 binaries linked from the mainnet solo mining guide until a final set is published at the top of that folder.

Report bugs on the Knots issue tracker. Security and update notices: bitcoinknots.org/list/announcements/join.

How to upgrade

If you are running an older version, shut it down. Wait until it has completely shut down, then run the installer on Windows, or copy over /Applications/Bitcoin-Qt on macOS, or bitcoind / bitcoin-qt on Linux.

Upgrading directly from very old Bitcoin Core or Knots is possible, but a data-directory migration can take time. Old Knots wallets are generally supported.

If your node was old, pruned, and followed invalid blocks, you may need to download the chain again. This release may ask at startup whether that resync is required.

What happened

BIP-110, in alignment with the vast majority of node policy, attempted to reject use of the network for arbitrary data storage while leaving ordinary payments alone. It was a user-activated softfork: a tighter rule that old software can still follow, and that nodes could enforce even if miners did not want it. It is not this hardfork. A hardfork is a break away from abuse of the Bitcoin network. The change to the BLAKE2b algorithm exists because that softfork was blocked, and because the reason it was blocked still matters.

Industrial mining groups that answer to shareholders, not node operators, rejected the cap and kept producing blocks that used transactions most nodes would not relay as a matter of policy. Anyone can still verify that history, but following it means accepting use of the network for arbitrary data storage, which every node operator on that chain must store at their own expense and, most importantly, risk.

On August 8, 2026, nodes enforcing BIP-110 stopped accepting blocks that did not support it, while most SHA256d mining power kept producing those blocks, so the money-only rules could not activate.

Proof of work later changed from SHA256d to BLAKE2b, a different algorithm, so today's SHA256d miners cannot add blocks here. The first BLAKE2b block is 961640 (30 August 2026). The pools that buried BIP-110 lose their lock on this chain. In that sense the hardfork "fires" the incumbent miners and lets a new market form around a ledger that is money only.

People asked for Bitcoin as money only. The mining power that refused them also stalled the chain. A new proof-of-work algorithm takes that mining power off the board.

Temporary limits on arbitrary data storage began at height 961640 with BLAKE2b, not on August 8. They are not a leftover BIP-110 miner-vote schedule. They apply to the new-style blocks until 1 September 2027, 00:00 UTC, using the previous block's median time past. That clock only moves forward, so the cutoff cannot flicker. While those limits are on, a block may also be no larger than about 300 kB serialized / 800,000 weight units. Coins created before the fork can still be spent under the old script rules. Continuing those limits after that date is a later choice for node operators; the BLAKE2b algorithm remains.

What this release changes

This build is a backward-incompatible protocol change. Other software, including third-party wallets, may need an upgrade to stay compatible. This release lists these items together:

  • Fix poison blocks (CVE-2013-2292)
  • Fix unintentional fees (CVE-2020-14199)
  • Fix block transaction-count mutation (CVE-2017-12842)
  • Fix for block-withholding attacks
  • Minor changes to BIP-110 (Reduced Data Temporary Softfork) activation and expiry
  • Temporary 800,000 weight-unit cap, about 300 kB serialized
  • BLAKE2b proof of work
  • Efficiency improvements for mining hardware
  • Future-proofing for merge-mined sidechains
  • Future-proofing for 40-bit block times

If you also spend on the SHA256d chain, use the opt-in SIGHASH_UNIFIED format and send the coins to yourself first. A pre-fork spend can otherwise be copied onto the other chain. Wait for confirmation as usual. See Knots PR 357.

Notable changes

The rejecttokens spam filter is on by default, and it now also detects Counterparty transactions.

getblockheader and getblock now include v2 header fields: txcount (when known; it replaces the deprecated nTx key), header_version, nonce2, nonce3, extranonce, time_offset, header_flags, xor_key, xor_key_mask_clear_bits, and mm_rhs.

Compatibility

Bitcoin Knots is supported on Linux, macOS 13+, and Windows 10+. It is not recommended on unsupported systems.

Known bugs

In several places, including the GUI transaction-details dialog and the vsize field in many RPC results, transaction virtual size may omit an unusually high sigop count (-bytespersigop) or datacarrier penalties (-datacarriercost). That can report a lower virtual size than mempool or mining actually uses.

This release still does not include updated translations. The shared Bitcoin Transifex repository is disrupted, and Knots may be unable to refresh translations until that is resolved.

What this means for node operators

  • If you already upgraded: You can continue using your existing Bitcoin data directory normally. No blockchain re-download or movement of funds is required.
  • If you are switching from Bitcoin Core or an older Bitcoin Knots release: That software may have followed the SHA256d chain. On startup, this release usually notices those extra blocks, walks back to the fork, and then downloads the BLAKE2b chain. That automatic walk-back is only for SHA256d blocks at or after the fork. If a BLAKE2b block itself breaks the data or size rules, you still need -reindex to rebuild the database from blocks you already have.
  • A pruned node deletes old blocks to save disk space. If you waited so long that the walk-back blocks are already gone, or the node followed invalid blocks after a late upgrade, rebuild the node and download the chain again. This release may ask at startup whether that resync is required.
  • You do not need to move your bitcoin. Coins created before the fork remain spendable.
  • After the BIP-110 softfork, Bitcoin Core and older Bitcoin Knots still require SHA256d and follow a different blockchain. You need a Knots version that includes the BLAKE2b change. Source: github.com/bitcoinknots/bitcoin. RC5 binaries are in the test directory on the mainnet solo mining guide.
